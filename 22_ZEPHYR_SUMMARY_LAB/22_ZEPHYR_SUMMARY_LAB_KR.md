# 22. 전체 커리큘럼 정리

## 이 실습에서 배우는 것

01번부터 21번까지 다룬 Zephyr의 핵심 개념들을 한 번에 정리합니다. Zephyr는 단순히 "또 다른 RTOS"가 아니라, **정적 구성을 선호하고, 스레드를 종류별로 나누며, 소스에서 직접 빌드하는 생태계**라는 일관된 설계 철학을 갖고 있습니다. 지금까지의 실습을 되짚으며 이 철학이 어떻게 구체적인 API로 드러나는지 확인합니다.

## Zephyr 설계 철학 3가지

### 1. 정적 구성을 선호한다

`K_THREAD_DEFINE`처럼 **컴파일 시점에 다 정해두는 방식**을 관용적으로 씁니다. 스택도 `K_THREAD_STACK_DEFINE`으로 미리 선언해야 합니다. 이건 메모리가 극히 제한된 소형 칩까지 함께 지원하기 위해 "실행 전에 필요한 자원을 최대한 예측 가능하게 만들자"는 철학에서 나온 설계입니다.

### 2. 스레드를 "종류"로 나눈다

협조적(Cooperative)과 선점형(Preemptible)이라는 **완전히 다른 두 가지 스케줄링 규칙을 스레드마다 선택**할 수 있습니다(02, 04번 실습). 이건 "정말 방해받으면 안 되는 짧은 작업"과 "일반적인 작업"을 명확히 구분하고 싶을 때 강력한 도구가 됩니다.

### 3. 소스에서 직접 빌드하는 생태계다

`west`로 항상 소스에서 직접 빌드하기 때문에 `prj.conf`(Kconfig) 옵션을 자유롭게 켜고 끌 수 있습니다. 19번 실습(Power Management)에서 본 것처럼, 이 특성 하나로 "코드 수정 없이 옵션 하나로 자동 절전" 같은 게 가능해집니다.

## 핵심 API 정리표

| 영역 | 핵심 API | 한 줄 요약 |
|---|---|---|
| 스레드 생성 | `K_THREAD_DEFINE` / `k_thread_create` | 정적/동적 두 가지 생성 방식 |
| 우선순위 | 숫자가 작을수록 높음, 음수=협조적/0 이상=선점형 | Zephyr 고유의 이중 스케줄링 모델 |
| 이벤트/신호 | `k_sem` | ISR에서도 그대로 호출 가능한 통일된 API |
| 상호배제 | `k_mutex` | Priority Inheritance가 기본 내장 |
| 데이터 전달 | `k_msgq` | 고정 크기 항목을 FIFO로 전달 |
| 다중 대기 | `k_poll` | 세마포어·큐·시그널을 한 번에 감시하는 범용 API |
| 경량 이벤트 | `k_poll_signal` | 값 하나를 가볍게 전달 |
| 비트 조건 | `k_event` | AND/OR 다중 조건 대기 |
| 타이머 | `k_timer` | 콜백이 ISR 컨텍스트에서 실행됨(주의 필요) |
| 스택 확인 | `k_thread_stack_space_get` | 바이트 단위 여유분 확인 |
| 자원 보호(ISR 경합) | `irq_lock` / `k_spinlock` | ISR과 경합하는 데이터는 스케줄러 락이 아니라 이걸로 |
| 절전 | `CONFIG_PM=y` | Kconfig 한 줄로 자동 절전 |
| CPU 사용률 | `k_thread_runtime_stats_get` | 표준화된 이식성 있는 API |

## 전체 커리큘럼 한눈에 보기

| 번호 | 핵심 한 줄 요약 |
|---|---|
| 01 | `K_THREAD_DEFINE`은 컴파일 시점에, `k_thread_create`는 런타임에 스레드를 만든다 |
| 02 | 숫자가 작을수록 우선순위가 높고, 음수는 협조적 / 0 이상은 선점형이다 |
| 03 | 스레드는 `return`으로 스스로 끝나거나 `k_thread_abort`로 강제 종료된다 |
| 04 | 협조적 스레드는 같은 우선순위끼리도 자동 교대되지 않는다 — `k_yield()`가 필요하다 |
| 05 | 낮은 우선순위 스레드가 자원을 쥐면 높은 우선순위도 오래 기다릴 수 있다 (우선순위 역전) |
| 06 | Idle Thread는 정말 할 일이 없을 때만 실행된다 |
| 07 | `k_sem_give`는 ISR에서 별도 버전 없이 그대로 호출 가능하다 |
| 08 | `k_sem`의 초기값/최댓값만 바꾸면 Counting Semaphore가 된다 |
| 09 | `k_mutex`는 Priority Inheritance가 기본 내장이다 |
| 10 | `k_msgq`는 고정 크기 데이터를 스레드 간에 전달한다 |
| 11 | `k_poll`은 여러 종류의 커널 객체를 한 번에 감시할 수 있다 |
| 12 | Poll Signal은 `k_poll`과 짝을 이루는 경량 값 전달 이벤트다 |
| 13 | `k_event`는 비트마스크로 AND/OR 다중 조건을 표현한다 |
| 14 | `k_timer`의 콜백은 스레드가 아니라 ISR 컨텍스트에서 실행된다 |
| 15 | `k_thread_stack_space_get`은 바이트 단위로 스택 여유분을 알려준다 |
| 16 | 여러 Mutex는 항상 같은 순서로 잠가야 Deadlock을 피한다 |
| 17 | ISR과 경합하는 데이터는 `k_sched_lock`이 아니라 `irq_lock`/`k_spinlock`으로 보호한다 |
| 18 | ESP32-S3에서 Zephyr는 AMP 구조 — 코어마다 별도 OS 이미지다 |
| 19 | `CONFIG_PM=y` 하나로 코드 수정 없이 자동 절전이 가능하다 |
| 20 | `k_thread_runtime_stats_get`은 이식성 있는 표준 CPU 사용률 API다 |
| 21 | `k_msgq` + `k_mutex`를 조합하면 실전 Producer-Consumer 패턴이 된다 |
| 22 | (이 파일) 정적 구성 선호, 스레드 이원화, 소스 빌드 생태계 — 세 가지 철학이 모든 API를 관통한다 |
