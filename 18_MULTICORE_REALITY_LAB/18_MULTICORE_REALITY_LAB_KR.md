# 18. SR110에서의 멀티코어 — 이종(Heterogeneous) AMP 아키텍처

## 이 실습에서 배우는 것

SR110용 Zephyr 포트도 ESP32-S3처럼 **AMP(Asymmetric Multi-Processing)** 멀티코어 모델을 씁니다 — 다만 ESP32-S3의 PROCPU/APPCPU와 달리 두 코어가 동일하지 않습니다. SR110은 **Arm Cortex-M55**(Ethos-U55 NPU 동반, "성능 도메인")와 **Arm Cortex-M4**("효율 도메인")를 짝지은 구조입니다 — Zephyr 공식 `sr100_rdk` 보드 페이지와 Synaptics 제품 브리프 양쪽에서 확인됩니다. 이번 실습은 코드 재현보다는, 이 이종 구조가 정확히 무엇을 의미하고 코어 간 통신이 실제로 어떻게 이뤄지는지 이해하는 데 집중합니다.

## AMP 구조 이해하기

| 항목 | 설명 |
|---|---|
| 커널 이미지 | **코어마다 별도의** OS 이미지 (M55용, M4용 각각 따로 빌드) |
| Thread 배치 | 각 코어가 자기 이미지 안의 스레드만 알고, 다른 코어의 스레드 존재 자체를 모름 |
| 코어 간 통신 | **확인됨**: Zephyr 표준 **mbox API** + 8바이트 공유메모리 — 다른 일부 Zephyr AMP 보드처럼 OpenAMP/RPMsg를 쓰는 게 아님 |
| 빌드 방식 | M55 타깃은 `sr100_rdk/sr100/m55`. M4 쪽은 별도 빌드 타깃이 필요함(아래 TODO/VERIFY 참고) |
| 시리얼 출력 | TODO/VERIFY: 두 코어가 공유된 230400bps 8N1 콘솔에서 각자 독립적으로 `printk()`를 쓸 수 있는지, 아니면 기본적으로 한쪽 코어만 그 UART를 소유하는지 |

## 왜 이렇게 설계됐는가

ESP32-S3의 AMP 모델(두 개의 *대칭적인* Xtensa 코어를 쓰고, 역할 분담(통신 스택 vs 애플리케이션)은 대체로 소프트웨어/제품 차원의 선택)과 달리, SR110의 M55/M4 분리는 **하드웨어 레벨의 전력/성능 등급 구분** 결정입니다. 제품 브리프에서 이 점을 직접 설명합니다 — M55(Ethos-U55 NPU 동반)는 무거운 AI 추론 작업을 위한 "성능 도메인"이고, M4는 더 가볍고 전력을 아끼는 작업을 맡아 M55가 더 오래 꺼져 있을 수 있게 하는 "효율 도메인"입니다. 이는 SR110의 4단계 전력 모드(active/low-power/ULP AON/power-down)와 맞물립니다 — M4(그리고 AON 아일랜드)가 SoC를 저전력 상태로 유지하면서도 이벤트에는 반응할 수 있게 하고, 실제로 무거운 연산이 필요할 때만 M55를 깨우는 구조입니다.

## 관찰 포인트

- 지금까지의 01~17번 실습은 전부 **한 코어(M55)**에서만 동작했습니다 — 여러 스레드를 만들었지만, 그건 "한 코어 안에서의 멀티스레딩"이었지 "두 코어를 동시에 쓴 것"은 아니었습니다
- AMP 구조에서는 코어 간 통신 자체가 명시적인 설계 대상입니다 — 어떤 데이터를, 언제, 어떤 프로토콜로 주고받을지를 처음부터 정의해야 합니다. 같은 메모리 공간을 자유롭게 공유하는 방식과는 근본적으로 다른 접근입니다
- 실무에서 SR110의 두 코어를 모두 활용해야 하는 프로젝트라면, 이 AMP 구조와 mbox 기반 IPC 설계를 프로젝트 초기 단계부터 고려해야 합니다 — 나중에 코드 한 줄만 바꿔서 될 일이 아니라, 프로젝트 구조 자체를 처음부터 두 개의 독립된 이미지로 설계해야 합니다
